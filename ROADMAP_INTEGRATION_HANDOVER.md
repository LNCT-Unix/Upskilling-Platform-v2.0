## 1. Project Overview

### 1.1 Purpose

The Roadmap Integration gives each user a **personalized AI-generated learning roadmap** after they complete an assessment. Instead of a generic course list, every user receives a step-by-step plan that is tailored to:

- Their current skill strengths and gaps (from assessment results)
- Their target role (e.g., "Backend Engineer")
- How many hours per week they can study

The roadmap is generated by **Google Gemini AI**, stored in **MongoDB**, and served through the existing **Spring Boot** gateway so the React frontend never needs to talk to Node.js directly.

### 1.2 Overall Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                     React Frontend                          │
│          (port 5173 — Vite dev server)                      │

│  1. Verifies x-internal-secret header                       │

└────────────┬───────────────────────┬────────────────────────┘
```

### 1.3 Key Design Decisions

| Decision | Reason |
|----------|--------|
| React never calls Node.js directly | Spring Boot handles all auth; Node.js is an internal service only |
| Node.js uses `x-internal-secret` header | Prevents any external caller from accessing Node.js directly |
| Spring Boot grades answers — never trusts frontend | Security: correctness values from frontend cannot be trusted |
| userId injected by Spring Boot, not from request body | Prevents spoofing of another user's roadmap |
| MongoDB stores roadmaps (not PostgreSQL) | Roadmaps are large, versioned, unstructured documents — ideal for MongoDB |
| `requestId` for idempotency | Prevents duplicate roadmap generation on network retry |

#### `RoadmapIntegrationService.java` (Service)
**Path:** `gateway/src/main/java/com/aiupskillingplatform/services/roadmap/RoadmapIntegrationService.java`

The **orchestration layer**. This is where the business logic lives. Its `generateRoadmap()` method does the following in sequence:

**Step-by-step Roadmap Generation Flow:**

```
Step 1: Resolve the Track
   → Try trackId from request (UUID lookup in PostgreSQL)
   → Fallback: try trackSlug from request
   → Final fallback: use "backend-development" track

Step 2: Find the user's latest completed assessment attempt
   → Query: findTopByUserIdAndTrackSlugAndStatusOrderByStartedAtDesc (COMPLETED)
   → Fallback 1: findTopByUserIdAndTrackIdOrderByStartedAtDesc (any status)
   → Fallback 2: findTopByUserIdOrderByStartedAtDesc (any track)
   → If no attempt found: use zero-score defaults

Step 3: Load all graded question responses for that attempt
   → Query: findByAttemptIdOrderByQuestionOrderAsc
   → For each response: look up the linked skill name and slug
   → Build QuestionItemDTO list (questionId, skillSlug, difficulty, isCorrect)

Step 4: Load all skills for the track from PostgreSQL
   → Query: skillRepository.findByTrackIdAndActiveTrue(trackId)
   → Fallback: findByActiveTrueOrderBySortOrderAsc (all active skills)

Step 5: Load user's skill mastery from PostgreSQL
   → Query: masteryRepository.findByUserId(userId)
   → Map each skill to: status (LOCKED/UNLOCKED), masteryScore
   → Build SkillItemDTO list

Step 6: Load skill dependency edges (DAG) from PostgreSQL
   → Query: dependencyRepository.findByTrackId(trackId)
   → Fallback: dependencyRepository.findAll()
   → Build DependencyItemDTO list (prerequisite → dependent pairs)

Step 7: Construct GenerateRoadmapPayloadDTO
   → Combine: userId, trackId, assessmentRef, targetRole,
              studyHoursPerWeek, assessment summary,
              questions list, skills list, dependencies list

Step 8: Call NodeRoadmapClient.generateRoadmap(payload)
   → Node.js calls Gemini AI
   → Gemini returns structured roadmap JSON
   → Node.js saves to MongoDB
   → Response proxied back to frontend
```

## 3. Backend Working

### 3.1 How Spring Boot Communicates with Node.js

Spring Boot uses `NodeRoadmapClient` (a synchronous `RestClient`) to send HTTP requests to the Node.js service. Every request automatically carries the `x-internal-secret` header, which Node.js verifies using a timing-safe comparison against its `INTERNAL_API_KEY` environment variable.

```
Spring Boot                                Node.js
-----------                                -------
RestClient.post("/api/roadmaps/generate")
  .header("x-internal-secret", secret)  →  verifyInternalAuth middleware checks header
  .body(GenerateRoadmapPayloadDTO)       →  validateRoadmapRequest middleware validates body
                                         →  createRoadmap() controller called
                                         →  Gemini AI generates roadmap
                                         →  Saved to MongoDB
                                    ←    JSON roadmap document returned
ResponseEntity<String> proxied to frontend
```

### 3.2 Authentication and Internal Security

**Frontend ↔ Spring Boot:**
- Frontend sends `Authorization: Bearer <JWT>` on every request
- Spring Boot's JWT filter validates the token and populates the `Authentication` object
- The controller calls `getAuthenticatedUser()` which rejects anonymous calls with `401`
- The user's UUID is loaded from PostgreSQL using their email (from the JWT)

**Spring Boot ↔ Node.js:**
- Spring Boot injects `x-internal-secret` header on every request to Node.js
- Node.js applies `verifyInternalAuth` middleware to all `/api` routes
- If the secret is missing or wrong, Node.js returns `401`
- The `userId` is injected by Spring Boot into the request body — Node.js trusts it because only Spring Boot (which verified the JWT) can pass the internal secret

**Security guarantee:** The frontend never sees the internal secret. Node.js is never accessible from outside. User IDs are always extracted from Spring Security context, never from request body.

#### PATCH `/api/roadmaps/{roadmapId}/progress`
Updates the status of a step or specific topic within a step.

**Request:**
```
PATCH /api/roadmaps/60c72b2f9b1d8b2badbee123/progress
Authorization: Bearer <JWT>
Content-Type: application/json
```

**Request Body:**
```json
{
  "stepId": "step-1",
  "topicId": "topic-1",
  "status": "COMPLETED"
}
```

- `stepId` — required. The step to update.
- `topicId` — optional. If provided, updates the topic; parent step status is auto-derived.
- `status` — required. Must be one of: `NOT_STARTED`, `IN_PROGRESS`, `COMPLETED`.

**Success Response (200):**
```json
{
  "success": true,
  "data": {
    "percentComplete": 42,
    "steps": [ ... ]
  }
}
```

**How `percentComplete` is calculated:**
- If a step has topics: count each topic as 1 unit
- If a step has no topics: count the step itself as 1 unit
- `percentComplete = (completedUnits / totalUnits) × 100`, rounded to nearest integer

---

### 3.4 How Roadmap Progress is Stored

Progress is stored **entirely in MongoDB** in the `roadmaps` collection. When PATCH is called:
1. Spring Boot forwards `userId` + `stepId` + `topicId` + `status` to Node.js
2. Node.js finds the roadmap document by `_id` AND `userId` (ownership check)
3. Node.js updates the topic or step status in the embedded document
4. Node.js recalculates `percentComplete`
5. The updated document is saved back to MongoDB
6. The full updated roadmap document is returned

### 4.3 Generating a Roadmap After Assessment

Call this **once** after the user finishes their assessment:

```javascript
async function generateRoadmap(trackSlug, trackId, targetRole, studyHoursPerWeek) {
  const response = await fetch('/api/roadmaps/generate', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${token}`,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      trackSlug,         // e.g. "backend-development"
      trackId,           // UUID of the track
      targetRole,        // e.g. "Backend Engineer"
      studyHoursPerWeek, // e.g. 10
      requestId: crypto.randomUUID() // prevents duplicate generation on retry
    })
  });

  if (!response.ok) throw new Error('Roadmap generation failed');
  const data = await response.json();
  return data.data; // the roadmap object
}
```

> **Important:** Generation can take **30–60 seconds** because Gemini AI is running. Show a loading spinner and do not timeout early.

### 4.4 Fetching the Active Roadmap

Call this when the user visits the roadmap page:

```javascript
async function fetchRoadmap(trackId) {
  const url = trackId
    ? `/api/roadmaps/me?trackId=${trackId}`
    : '/api/roadmaps/me';

  const response = await fetch(url, {
    headers: { 'Authorization': `Bearer ${token}` }
  });

  if (response.status === 404) return null; // No roadmap yet
  if (!response.ok) throw new Error('Failed to fetch roadmap');
  const data = await response.json();
  return data.data;
}
```

### 4.6 Updating Progress

When the user clicks "Mark as Complete" on a topic or step:

```javascript
async function updateProgress(roadmapId, stepId, topicId, status) {
  const body = { stepId, status };
  if (topicId) body.topicId = topicId;

  const response = await fetch(`/api/roadmaps/${roadmapId}/progress`, {
    method: 'PATCH',
    headers: {
      'Authorization': `Bearer ${token}`,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify(body)
  });

  if (!response.ok) throw new Error('Failed to update progress');
  const data = await response.json();
  return data.data; // updated roadmap with new percentComplete
}
```

**Valid status values:** `NOT_STARTED`, `IN_PROGRESS`, `COMPLETED`

### 5.4 MongoDB Collection Structure

MongoDB collection: `roadmaps` (in `upskilling_roadmaps` database)

The roadmap document schema (defined in `roadmap-service/src/models/Roadmap.js`):

```
Roadmap document
├── userId (String — PostgreSQL user UUID)
├── trackId (String — PostgreSQL track UUID)
├── targetRole (String)
├── assessmentRef (String — PostgreSQL attempt UUID)
├── requestId (String — idempotency key, unique index)
├── status (ACTIVE | ARCHIVED)
├── version (Number — increments on regeneration)
├── percentComplete (Number — 0 to 100)
├── studyHoursPerWeek (Number)
├── generation
│   ├── model (Gemini model name)
│   ├── promptVersion
│   └── createdAt
├── assessment (snapshot of PostgreSQL assessment data)
│   ├── assessmentId
│   ├── trackSlug
│   ├── difficulty
│   ├── totalQuestions
│   ├── correctCount
│   ├── wrongCount
│   ├── score
│   └── questions[] (per-question graded results)
├── skillAnalysis[] (per-skill mastery analysis)
├── skillGaps[] (slugs of gap skills)
└── steps[]
    ├── stepId, sequence, category, title, skill, level
    ├── estimatedHours, status, reason, prerequisites[]
    ├── topics[] (topicId, name, points[], status)
    ├── resources[] (title, url, type, platform, description)
    └── project (title, description)
```

MongoDB indexes (already defined in `Roadmap.js`):
- `{ userId, trackId, status }` — for active roadmap lookup
- `{ userId, trackId, version: -1 }` — for history sorted by version
- `{ userId, requestId }` unique partial — for idempotency
